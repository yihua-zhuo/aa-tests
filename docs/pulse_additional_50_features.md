# Pulse 功能扩展需求：额外 50 项高级功能

> 基于《Pulse 当前功能说明》（Clay Dashboard / Pulse 1.0.0，SQLite schema v14）扩展。
> 本文件是新增功能需求草案，不代表功能已经实现。现有能力和技术限制以原始文档为准。
> 目标：在保留现有项目、任务、分析、实时协作、权限、多租户与运维能力的基础上，补齐企业级规划、流程自动化、知识管理、数据治理和平台扩展能力。

## 1. 需求编写原则

- **不重复建设**：优先扩展现有项目、任务、评论、通知、活动流、审计、工作区、功能开关和 API 体系。
- **服务端强制校验**：所有新增入口都必须在 API 层执行身份、工作区、项目可见性和字段级权限检查，不能只隐藏前端按钮。
- **可审计、可恢复**：审批、规则、配置、权限、导入导出、自动执行和数据修复均记录操作者、时间、原因、前后状态及关联请求 ID。
- **兼容现有栈**：需求以 React 19、Hono、Zod、SQLite WAL、SSE/WebSocket 和当前单进程部署为起点；需要外部服务或架构拆分的功能明确标记为架构升级项。
- **版本化和幂等**：规则、工作流、指标定义、文档、基线和审批策略均应有版本；异步任务、重试和事件消费必须定义幂等键。
- **逐步交付**：每项需求都包含目标能力与关键验收边界，实施时应进一步拆成数据模型、API、UI、迁移、安全测试和端到端测试。

## 2. 优先级建议

| 优先级 | 含义           | 建议范围                                                     |
| ------ | -------------- | ------------------------------------------------------------ |
| P0     | 安全或治理基础 | 权限模拟、审计强化、数据分类、异步任务可靠性、迁移与恢复治理 |
| P1     | 核心业务增值   | OKR、阶段门、依赖图、重复任务、知识库、工作流、自定义指标    |
| P2     | 企业协作扩展   | 客户门户、SSO/SCIM、多工作区组织、插件市场、AI 助手          |

优先级仅为建议，不能替代产品评审、技术评审和风险评估。

## 3. 新增功能清单（50 项）

### 1. 战略目标树与 OKR 联动

**领域：** 战略目标与产品治理

**需求说明**

支持公司、部门、工作区、项目四级目标树；目标可配置负责人、权重、周期、关键结果、基线值、目标值与实际值；项目里程碑和任务可关联关键结果；系统按权重计算进度，并区分手工更新与数据驱动更新。

**复杂度与验收重点**

目标树循环引用、跨工作区越权、权重合计异常、历史周期锁定、目标删除后关联处理。

**通用验收要求**
- 未授权请求返回一致的 401/403/404 语义，且不能通过搜索、计数、错误消息或实时事件泄漏不可见资源。
- 关键写操作必须支持并发冲突检测；可重试操作应具备幂等语义。
- 新增 API 纳入 OpenAPI 3.1 与 Zod schema；新增页面通过键盘操作、移动端布局和 axe 扫描。
- 单元测试覆盖正常、边界、权限拒绝、并发冲突、重复请求和失败恢复场景；重要流程补充 Playwright E2E。

## 4. 跨功能非功能要求

### 4.1 安全与权限

1. 所有功能默认遵循工作区隔离和项目可见性规则；不得假设前端过滤等于安全边界。
2. 对导出、批量操作、AI、外部集成、客户门户和临时授权采用最小权限原则。
3. 所有秘密使用专用密钥管理方式保存；日志、活动摘要、错误响应与审计详情不得记录明文密码、Cookie、PAT、Webhook secret 或 OAuth token。
4. 对 SSRF、CSRF、XSS、IDOR、重放、请求走私、文件解析和提示注入分别设计防护与测试。
5. 高风险操作应支持二次确认、理由填写、审批或短时重新认证。

### 4.2 数据模型与迁移

1. 新表、索引、约束与迁移脚本需纳入 schema 版本管理；升级前生成一致性备份，并验证迁移前置条件。
2. 迁移采用可观测、可续跑的步骤；对不可逆数据变换提供备份恢复方案，不得承诺无法保证的数据级自动回滚。
3. 大批量重算、索引回填和附件迁移应支持 dry-run、进度、取消/续跑与错误明细。
4. 需要外部队列、对象存储、企业 IdP、向量数据库或 AI 模型的功能必须明确列出依赖、成本、故障模式和降级行为。

### 4.3 API 与并发

1. 新增写接口使用统一错误结构，包含稳定错误码；必要时返回 `reqId`、冲突资源版本和可安全展示的说明。
2. 对重复提交使用幂等键或数据库唯一约束；对长任务使用任务 ID 查询状态，而不是保持长时间 HTTP 请求。
3. 对分页、排序、过滤和批量数量设置服务端上限；所有排序字段使用白名单，禁止拼接任意 SQL。
4. 对版本化资源使用乐观锁；事件推送采用游标或版本号检测缺口，并提供可靠的重新同步机制。

### 4.4 可观测性与运维

1. 每个后台任务至少记录排队时间、开始/结束时间、耗时、重试次数、结果和失败原因。
2. 为队列积压、失败率、自动化循环阻断、审批超时、存储容量、导出量和权限变更建立指标。
3. 管理员可以查看失败任务并执行授权范围内的重试、取消或死信处理；相关操作写入审计。
4. 新功能应能通过功能开关灰度启用；关闭入口不能替代 API 权限检查，停用功能时需定义既有数据的读取和导出策略。

### 4.5 性能与可用性

1. 列表与图谱采用分页、游标或虚拟滚动；高成本报表和全量索引重建进入后台任务。
2. 为关键接口定义延迟目标、最大载荷、并发限制和降级策略；目标值需在性能测试后由团队确认。
3. 对 SQLite 写锁竞争、WAL 增长、长事务和备份期间负载进行压测；多实例部署前必须解决单机数据库、文件存储和单进程 Worker 的限制。
4. 实时事件必须经过服务端权限裁剪；断线重连、重复事件、事件缺口和客户端过期状态都应有测试。

## 5. 建议实施阶段

### 阶段 A：安全和运行基础

- 权限策略模拟器
- 数据分类与字段级访问控制
- 不可篡改审计导出
- 异步队列与多实例 Worker
- 数据库迁移编排与回滚检查
- 附件对象存储与恶意文件隔离
- 恢复演练与灾难恢复目标

### 阶段 B：项目规划和执行

- OKR 与战略目标树
- 项目组合评分、健康度、基线、关键路径
- 阶段门、范围变更、资源容量规划
- 多层任务、重复任务、SLA、自动分派、交付物验收

### 阶段 C：协作与流程自动化

- 协作文档、知识图谱、决策日志、会议纪要
- 可视化工作流、审批代理、定时触发器、运行重放
- 事件总线、连接器目录、规则沙箱

### 阶段 D：经营分析与企业化

- 自定义指标、异常检测、数据质量、情景预测、预算
- 自助报表、指标血缘、跨工作区组织、SSO/SCIM
- 客户门户、插件市场、AI 项目助手

## 6. 交付物要求

每项功能进入开发前，至少补齐以下交付物：
1. 用户故事、角色矩阵和明确的范围内/范围外说明。
2. 状态机、关键业务规则、异常路径与权限矩阵。
3. 数据字典、索引、唯一约束、迁移与回滚/恢复方案。
4. API 契约、请求/响应示例、错误码、分页和幂等策略。
5. 页面流程、空状态、加载状态、失败状态、移动端和无障碍要求。
6. 审计字段、指标、日志脱敏规则、告警与运维手册。
7. 单元、集成、权限、安全、性能和端到端测试用例。
8. 功能开关、灰度方案、上线检查、回滚触发条件和数据兼容说明。

## 7. 验收原则

- 不以“页面可见”作为完成标准；必须验证服务端行为、数据一致性和权限隔离。
- 不以单次成功作为异步功能完成标准；必须验证重试、重复投递、服务重启和依赖故障。
- 不以管理员账号测试替代完整权限测试；至少覆盖管理员、业务经理、项目经理、只读成员和跨工作区拒绝访问。
- 不以 mock 代替所有集成验证；涉及 SMTP、Webhook、对象存储、IdP、推送和外部模型时，应有契约测试及可重复的故障注入方案。
- 不将本文中的新增需求描述为现有已实现功能；每项应在产品评审后分配负责人、版本和验收状态。
