# OCR 方案评审：结论与 50 条改进点

> **评审对象**：`document-intelligence.md`（文档智能与 OCR 完整方案 V2）
> **评审日期**：2026-10-31
> **评审方式**：仅基于文档文本。未审查代码、真实基准数据和线上指标；文档引用的 `ocr-solution.md`、`ocr.md` 也未提供。
> 涉及 PaddleOCR 等第三方行为的判断，标注"需实测"，请以实验为准。
> **更新**：第一轮 50 条见第二节；第二轮复查补充的 23 条（#51–#73）见第五节。

---

## 一、结论：方案是否正确？

**总体判断：方向正确，治理成熟度高于常见 OCR 方案，但存在三类需要纠正或补强的问题。**

### 做对了的地方（建议保持）

| 设计                                             | 为什么对                                            |
| ------------------------------------------------ | --------------------------------------------------- |
| 原生优先（native-first），按页、按区域路由       | 能直接读文本层就不引入识别误差；混合 PDF 不整篇 OCR |
| 原文不可覆盖，候选只作证据，版本链可追溯         | 可审计，避免"静默改错"                              |
| 硬性风险不可被高分补偿，结果选择分层比较         | 防止高置信度掩盖漏页、漏字段、算术不平              |
| 区域/单元格复认优先于整页重跑                    | 成本低，定位准                                      |
| 阶段回放（输入输出哈希、参数、评分）             | 改动是否真的有效可复现                              |
| 分层基准 + Wilson 区间 + 发布门禁 + 最差分组门禁 | 不被平均数欺骗                                      |
| 灰度、注册表、审计、漂移、反馈池                 | 有闭环意识                                          |

### 需要纠正或补强的三类问题

1. **闭环存在"自证"风险。** 质量分、恢复收益、候选采纳、灰度晋级大量依赖同一套**启发式分数**，而不是标注真值。分数变高不等于真实错误变少（#13、#30、#31、#35、#36、#48）。
2. **高风险字段缺少"独立冗余"。** 现有"确认"主要来自同一模型的重复识别（#33），没有利用校验位、大小写金额互校、二维码、主数据等**与 OCR 无关的独立证据**（#15、#23、#24、#25、#28）。
3. **输入覆盖、安全与隐私有盲区。** Office 内嵌图片/文本框、文本层交叉验证的比较方式、输入加固、跨租户缓存与 PII 生命周期，文档都没有覆盖（#2、#5、#7、#12、#49）。

另有一处需要注意：**文本后处理**（§6.2）的几条规则可能改坏数据，并与"原始结果不可覆盖"的原则冲突（#19）。

### 优先级说明

| 标记 | 含义                                     | 数量 |
| ---- | ---------------------------------------- | ---- |
| `P0` | 影响正确性、误判风险或合规，建议优先处理 | 20   |
| `P1` | 明显提升识别率、可靠性或可运维性         | 28   |
| `P2` | 优化项，按需排期                         | 2    |

## 二、50 条改进点

### A. 输入与原生抽取（1–10）

### 01 · 扫描 PDF 优先提取内嵌原图，而不是整页重新栅格化 `P1`

- **问题**：§5.1 对扫描 PDF 用 pypdfium2 渲染，默认从 200 DPI 起步。若页面本质是 300–600 DPI 的位图，渲染到 200 DPI 会损失细节；若原图只有 150 DPI，放大到 300/400 DPI 不会增加信息，只增加耗时。
- **建议**：整页单图的扫描页直接取内嵌图像流（原始分辨率与色彩），目标 DPI 以"原图有效 DPI"封顶。记录图像编码类型。有损 JBIG2 有过扫描件数字被相近字形替换（如 6↔8）的已知问题，这类错误任何 OCR 都发现不了，应在预检中标记"JBIG2 有损风险"，并对金额页提高复核等级。

### 02 · PDF 文本层的可信度判定与交叉验证：覆盖不足，且比较方式会掩盖数字错误 `P0`

- **问题**：§5.2 的可信度只看长度、替换符、私用区和可读字符占比，识别不出"看起来正常但内容错误"的文本层（典型：旧扫描仪或第三方 OCR 生成的隐形文本层）。交叉验证默认只抽 10%、最多 2 页，相似度 0.85 按去空白全文比较——千字页面里错一个金额数字，相似度仍约 0.999，不会触发 `text_layer_mismatch`。
- **建议**：
  - 检测"整页图像 + 不可见文本（render mode 3）"结构，标为"第三方 OCR 层"并提高抽样率。
  - 抽样改为风险分层：含金额、数字、表格的页必抽。
  - 除整体相似度外，单独比较数字 token 与关键字段，数字不一致即告警。
  - 检查 ToUnicode 缺失、CID 乱码映射。

### 03 · PDF 页面旋转、CropBox/MediaBox 与 bbox 坐标映射 `P1`

- **问题**：文档多处依赖"bbox 映射回 PDF point（72 DPI）"（§5.2-6、§11.3、§18.12）。页面带 `/Rotate`、CropBox 与 MediaBox 不一致或原点偏移时，pdfplumber 与渲染引擎坐标容易错位，区域复认会裁错位置，且不易察觉。
- **建议**：建立统一的旋转/裁剪/缩放坐标变换层，并加专项用例（90/180/270°、CropBox 偏移、非 A4、超大页）。区域复认前做自检："裁剪区域内识别文字"与"原 bbox 内文字"应大体一致，不一致则放弃该次复认。

### 04 · 原生 PDF 抽取遗漏表单域、注释与附件 `P1`

- **问题**：§6.1 只覆盖文本、行框和表格。可填写 PDF 的 AcroForm/XFA 字段值、批注（FreeText/Stamp）、嵌入附件、可选内容层（OCG 隐藏层）都不在页面文本流里，而合同、申请表恰恰常把关键值放在表单域里。
- **建议**：抽取后写入 DIR（`source=form_field` / `annotation`）。隐藏层、白色或极小字号文本标记为 `hidden`，既防漏也防注入（见 #34）。

### 05 · Office 文档的内嵌图片、文本框、图表、批注、修订痕迹未覆盖 `P0`

- **问题**：§4.2、§6.1 只用 python-docx/openpyxl/python-pptx 读段落、工作表和表格。docx/pptx 中的文本框、形状组、SmartArt、图表、脚注、批注，以及插入的图片（截图、扫描件、签章图）都不会被读取。修订痕迹中被删除的文字若被当成正文，会产生错误字段。
- **建议**：
  - 内嵌图片走区域 OCR（沿用 `embedded_image` 路由）。
  - 解析 `w:del` / `w:ins`，只采纳终稿，并标记"含修订"。
  - 覆盖文本框、形状、备注页、隐藏幻灯片，并带来源标记。
  - 为此类遗漏增加"覆盖率"质量信号。

### 06 · XLSX 的存储值与显示值、公式缓存、隐藏内容 `P1`

- **问题**：openpyxl 默认读公式文本，`data_only=True` 读缓存值（可能为空或过期）。单元格显示 `15%`、`¥1,280`，存储值却是 `0.15`、`1280`。隐藏行列、隐藏工作表、合并单元格、日期序列号都会影响下游字段。
- **建议**：DIR 单元格同时保存 `value`、`displayText`、`formula`、`numberFormat`；隐藏内容打标；日期与百分比按 numberFormat 解析；公式缓存缺失时标记，而不是默认当空值。

### 07 · 输入加固与沙箱 `P0`

- **问题**：§4.4 只覆盖路径穿越、token 和请求体大小。文件内容层面的攻击面文档未提及：图片解压炸弹、超大页面尺寸 PDF、畸形 PDF、docx/xlsx 的 zip 炸弹与 XML 实体膨胀、加密 PDF 的处理、含宏或 OLE 对象的 Office 文件。
- **建议**：
  - 设置 Pillow `MAX_IMAGE_PIXELS` 与页面面积上限。
  - 限制 zip 解压总量与压缩比；XML 解析使用 defusedxml。
  - 加密文件返回明确状态（如 `needs_password`），不要按失败重试 3 次。
  - sidecar 以非 root、无外网、只读挂载、CPU/内存限额运行；文件解析与模型推理进程隔离，崩溃互不影响。

### 08 · 格式覆盖与"静默跳过" `P2`

- **问题**：§3、§5.1 对 ZIP 等直接 `skipped`，包内扫描件从未被处理，用户也未必知道。iPhone 的 HEIC/HEIF、AVIF、JPEG 2000、旧版 `.doc/.xls/.ppt` 是否支持文档未说明。文本类文件若不探测编码（GBK/UTF-16/BOM），中文会乱码。
- **建议**：UI 对 `skipped` 显示原因，并提示"压缩包内文件未处理"；提供受限的安全展开（深度、数量、总大小、路径校验）；补齐 HEIC 等转换并保留 EXIF 方向；文本文件做编码探测并记录。

### 09 · 多文档合订扫描与页面级异常 `P2`

- **问题**：批量扫描常把多份单据合成一个 PDF，而现有流程以"文件"为单位评估、复核和校验。页内的空白页、分隔页、重复页、逐页方向不一致没有单独建模。
- **建议**：增加文档边界切分（分隔页、版式、页码、标题特征）；页面级方向与语言判断；空白与重复页标记；字段与算术校验在"逻辑文档"内计算，避免跨单据的合计互相污染。

### 10 · 预检阈值随内容自适应，并前移到采集端 `P1`

- **问题**：§7.1 的阈值是全局常数。像素总数 ≥ 300000 会把小票、裁剪截图误判为低分辨率（即使文字高度足够）；`sharpness` 依赖边缘方差，稀疏页面天然"偏模糊"；这些阈值是否对应真实 CER 拐点，文档没有依据。
- **建议**：低分辨率判定以实测文字高度为主、总像素为辅；清晰度只在文本区域内计算；用基准数据画"指标—CER"曲线，把阈值定在 CER 明显上升处，并按文档类型分别配置。同时在上传前端（Web/移动）做采集前预检（模糊、反光、边缘与透视提示），让 `retake` 在用户还在现场时触发，而不是识别完才提示。

### B. 识别、预处理与缓存（11–19）

### 11 · 检测与识别阶段的关键参数未进入实验矩阵 `P1`

- **问题**：§13.4 的对照实验只覆盖模型、mode、DPI、通道。检测输入边长上限与缩放策略、检测二值化与框阈值、框扩张比例（unclip）、识别 batch 与输入尺寸等，文档均未列出。高分辨率整页在检测阶段通常会被缩放到边长上限内，细小文字可能被"缩没"，此时单纯提高 DPI 未必有收益（需实测）。
- **建议**：把这些参数作为可配置实验变量，按文档类型（小票、发票、合同、表格）分别寻优，并写入运行时指纹，避免缓存误用。

### 12 · 缓存键可能不完整，复用范围未说明 `P0`

- **问题**：§12 的缓存键是 `sha256 + engine + engineModel + mode + dpi`。若声明语言与语言 profile、`OCR_PREPROCESS_GEOMETRY`、通道、Camelot/VLM/专用识别适配器的开关与版本、级联参数（最大阶段数、预算、复认遍数）不在 `engineModel` 指纹里，配置变化后会复用旧结果，而基准里看不出来（需确认）。此外复用是否按工作区隔离，文档没说（见 #49）。
- **建议**：缓存键改为"输入哈希 + 完整配置哈希（含上述全部会影响输出的参数与适配器版本）+ 租户范围"。增加命中抽检：定期重跑命中样本并比较输出，发现差异即整体失效。

### 13 · 光度候选的采纳标准存在自证风险 `P0`

- **问题**：§7.2 规定候选图"必须通过区域识别评分超过原图才会被采用"。若评分主要是识别置信度，增强产生的伪边缘可能让置信度更高、文字更错，等于用被优化的信号当裁判。
- **建议**：评分改用多信号一致性（候选与原图识别结果的数字 token 一致性、业务校验通过数、与独立引擎的一致性）。在标注集上统计"被采纳候选相对原图的真实 CER 变化"，不能稳定为负就降低其启用优先级。

### 14 · 印章遮挡文字：做颜色分离后再识别 `P1`

- **问题**：§5.1 把印章/签名隔离为独立 block，但印章压在金额、日期上的场景（发票专用章、合同骑缝章）仍会破坏下方文字。红通道只是实验变量，没有针对"印章重叠区域"自动启用。
- **建议**：对检测到印章重叠的区域，用 HSV/Lab 颜色分离生成"去章"图层再识别，并与原图结果做候选比较。弧形印章文字交给专用识别（约束同 #34），结果只作证据。

### 15 · 用二维码、条形码、MRZ 作为独立校验源 `P0`

- **问题**：方案的"确认"主要来自同一 OCR 引擎的重复识别（见 #33）。许多单据本身带机读冗余：发票、小票、快递面单上的二维码或条码，护照证件的 MRZ（含校验位）。它们与 OCR 完全独立，是现成的"第二来源"。
- **建议**：增加条码、二维码、MRZ 解码器，把解码出的金额、日期、编号与 OCR 字段比对。一致则升级为 `confirmed_independent`，冲突则作为硬性风险。

### 16 · 数字单元格的受限字符集重识别 `P1`

- **问题**：§11.3 的复认是同一识别器换边距或模式重跑，不约束输出字符集。金额列里的 `O/0`、`l/1`、`S/5`、`B/8` 混淆（§2.1 有混淆集）只在事后校验。
- **建议**：对类型已确定的数字、日期单元格，用受限字符集重识别（只保留 `0-9 . , - % ( ) ¥ $` 等），或接入数字专用模型（§20.3 Phase 2 已规划，可先做小规模验证）。验收指标用"数字单元格 CER 的变化"。

### 17 · 取字符级置信度与解码 top-k，而不是靠重跑得到 N-best `P1`

- **问题**：当前"N-best"来自多次裁剪重跑，慢且相关性高。一行整体 0.97 的置信度可以掩盖其中某一位数字只有 0.4 的情况，行级置信度对长行里的数字错误不敏感。
- **建议**：若引擎或自定义解码支持，输出字符级置信度和解码 top-k。对金额等字段用"最小字符置信度"做门槛，复核界面高亮最低置信字符。

### 18 · 语言检测：汉字共用、繁简体、页级语言、更多脚本 `P1`

- **问题**：§5.5 按脚本判断语言并在不符时重跑。中日文共用汉字，纯汉字页面仅凭脚本无法区分（需要假名占比等特征）；简体与繁体需要不同候选；一份文档不同页语言可能不同；profile 清单里没有西里尔、泰文、天城文等。
- **建议**：语言检测改为页级或区域级，加入假名/谚文占比与繁简判定；扩充 profile 并在基准中按语言分层评估；语料中没有的语言明确标注"未验证"。

### 19 · 文本后处理的歧义规则可能改坏数据，并与"原始结果不可覆盖"冲突 `P0`

- **问题**：§6.2 的归一包含"冒号、句末标点后补空格""CJK 与拉丁/数字边界补空格""全角数字分隔符归一"。若实现未排除特例，会改坏 `12:30`、`http://…`、比例 `1:2`、`订单号：AB123`（需精确匹配的字段）；`1，2，3` 这类列表被改成 `1,2,3` 后会与千分位产生歧义。这些改动落在 `ocr_text` 上，与 §1.1 的"原始结果不可覆盖"并不完全一致。
- **建议**：同时保存 `rawText` 与 `normalizedText`，不同用途用不同字段。全角逗号→半角仅在严格千分位模式（`\d{1,3}(，\d{3})+`）下进行；补空格规则排除"数字-冒号-数字"、URL、编号模式。用属性测试（property-based test）验证"归一不改变字段值"。

### C. 版面、表格与字段（20–29）

### 20 · 阅读顺序：质量信号不检测正确性，需要独立指标 `P1`

- **问题**：§10 的 `reading_order` 信号只检查 readingOrder 是否重复或缺失，不衡量顺序是否正确。§8.2 的栏分带是启发式；竖排（中日文）、跨栏说明、旁注都可能错序，且不会触发任何复核。
- **建议**：基准加入阅读顺序指标（Kendall τ、块序列编辑距离），建立多栏、竖排、杂志式版面样本。对合同条款等高风险类型，引入基于版面模型的阅读序候选，与启发式结果不一致时标记。

### 21 · 文档类型分类 + 按 schema 抽取关键信息，取代"文件名推断 + 列标签规则" `P0`

- **问题**：§14.2 的业务类型只按文件名推断，不读正文；§9.4 的关键字段类型由规则识别。文件名不可靠，规则也只知道"这是一个金额"，不知道它是"价税合计""税额"还是"单价"。
- **建议**：用版式 + 文本的轻量分类器识别发票、收据、合同、证件、银行回单等；为每类定义字段 schema（必填、格式、互相约束），再用关键信息抽取（KIE）模型或"规则 + 版面模型"落字段。门禁与阈值（如 `OCR_GATE_MAX_CER_<KIND>`）可绑定到真实分类。

### 22 · 字段"语义角色"与跨页字段关联 `P1`

- **问题**：§9.3 的业务约束靠列标签触发，对非表格单据（发票头部、合同条款里的金额）覆盖有限。"合计金额"常在最后一页，明细在前几页，当前校验主要停留在单个表格内。
- **建议**：给字段增加 `role`（总金额、税额、不含税金额、币种等）和键值关联证据（标签—值的位置关系与置信度）。对跨页、跨表的"总额—明细"做文档级对账。

### 23 · 引入校验位规则（价值高，几乎零误报） `P0`

- **问题**：§9.3 的"编号形态"只检查格式。很多编号自带校验位，能以接近确定性的方式发现 OCR 错误。
- **建议**：加入统一社会信用代码（GB 32100）、居民身份证号（ISO 7064 MOD 11-2）、银行卡号（Luhn）、IBAN（mod 97）、ISBN/VIN 等校验。校验失败升级为 `field_validation_failed`；校验通过可作为独立证据，提升字段的确认等级。

### 24 · 大小写金额、数字与文字互校 `P0`

- **问题**：中文银行回单、发票、支票、合同常同时出现小写金额和大写金额（壹万贰仟……），这是同一文档内天然的冗余，现有方案没有利用。
- **建议**：实现大写金额解析器并与小写金额比对；英文单据同理（amount in words）。二者一致可显著提高金额可信度，不一致则直接进入硬性风险。

### 25 · 数值语义：单位、量级、负数、中文数字 `P0`

- **问题**：§9.2 处理了千分位与小数点歧义，但没有提到：表头"单位：万元/千元"带来的量级；括号负数 `(1,234)`；尾随负号 `1,234-`；`CR/DR`；百分比与小数；中文数字（三万五千）；`¥/￥/RMB` 等币种写法。这些是财务表格最常见的语义错误源，且 OCR 本身并没有"错"。
- **建议**：从表头与表注中提取单位并写入列 schema；统一的数值语义解析器输出 `{value, unit, scale, sign, currency}`；在数值 CER 之外增加"语义数值准确率"。

### 26 · 税额、舍入规则与容差可配置 `P1`

- **问题**：§9.3 的"税额 ≈ 基数 × 税率，逐行比较"与合计求和，对容差、舍入方式（逐行舍入还是合计后舍入）、含税/不含税、多税率、币种小数位（JPY 0 位、KWD 3 位）都没有说明。容差过严会推高 review 率，过松会漏检。
- **建议**：容差与舍入策略按币种、文档类型配置。用基准样本统计各规则的误报率与漏报率，把误报率纳入规则上线门禁。

### 27 · 表格：采用标准 TEDS/GriTS，并让无框线表真正产出结构 `P1`

- **问题**：§13.2 用的是"简化 TEDS"，与公开基准不可直接比较；§18.13 也承认复杂合并表与超宽表覆盖有限。无框线表只生成 `borderlessTables` 候选标记，不输出单元格，下游仍然无法使用。
- **建议**：同时报告标准 TEDS/TEDS-S（可选 GriTS），并用公开数据集（PubTabNet、FinTabNet 类）做外部对标，另建中文业务表格集。无框线表输出带置信度的候选网格并进入级联，让"结构识别模型"与"对齐推断"择优。

### 28 · 领域词典、主数据匹配与热词偏置 `P1`

- **问题**：供应商、客户、产品、银行、地区名称是最常见的形近字错误来源，而企业通常有主数据。方案没有利用这类外部先验。
- **建议**：对公司名、银行名、地址、产品名与主数据做模糊匹配（编辑距离 + 字形相似），产出"建议值"和匹配得分。仍遵守"不覆盖原文"，只作证据与复核提示；词典命中率可纳入质量信号。

### 29 · 三层取值（raw / candidate / verified）与修订复用 `P1`

- **问题**：系统严格保留原文，这很好，但下游需要的是"当前最可信的值 + 状态"。§12 的缓存复用也只复用 OCR 文本：同一 sha256 已有人工修订时，新上传的副本不会受益。
- **建议**：字段 API 统一返回 `rawValue`、`candidates[]`、`finalValue` 与状态（`unverified` / `confirmed_independent` / `human_verified`），下游按状态消费。缓存命中时附带同哈希文件的人工修订作为"建议值"（需校验页面或区域一致）。

### D. 质量评估与级联（30–40）

### 30 · 质量分权重总和为 1.4，且随信号适用性漂移 `P0`

- **问题**：§10 表中 13 项权重之和为 1.40（0.25 + 0.10 + 0.20 + 0.15 + 0.15 + 0.10 + 0.10 + 0.10 + 0.05×5），靠"按权重和归一化"运作。无表格的页面上某些信号不适用，实际权重随之变化，使同一阈值（0.7/0.45）在不同文档类型上含义不同。另外 `key_region_missing` 既是加权信号又是硬性风险，存在重复计分。
- **建议**：改为"按文档类型的学习型质量模型"（例如预测"字段出错概率"的逻辑回归或梯度提升），特征沿用现有 13 个信号，用标注集训练并校准。硬性风险与分数分离，不再重复计入；可解释分量作为特征贡献展示。

### 31 · 置信度本身未校准，应先校准再入分 `P0`

- **问题**：识别置信度通常偏高（需实测），数字与相似字形尤甚。§10 以 0.25 权重直接使用，§10.2 的 0.85 关键字段门槛也是固定值。
- **建议**：先对识别置信度做校准（温度缩放或等渗回归），按语言、模型、字符类别（数字/字母/汉字）分别拟合。校准后的概率再进入质量模型与门槛。基准里同时报告校准前后的 ECE。

### 32 · 校准粒度：不要用"文档全对"做标签 `P1`

- **问题**：§13.2 的置信度校准用"全对结果"分箱，对长文档几乎恒为 0，可靠性图退化，ECE 也失去意义。
- **建议**：校准在行、字段、单元格层面进行（标签 = 该单元是否正确），再汇总到文档。输出风险—覆盖曲线（risk-coverage），并分语言、文档类型、字符类别报告。

### 33 · 复认"一致即确认"高估了独立性，需要异构引擎 `P0`

- **问题**：§11.3 的区域与单元格复认是同一模型换边距或模式重跑，错误高度相关（同一种形近字误判会稳定复现）。`confirmed` 因此容易给出虚假的安全感，并削弱硬性风险的触发。
- **建议**：把 §20.3 Phase 1 的"多引擎并行候选"前移，对关键字段用不同架构或训练数据的引擎（另一套 OCR，或只做读取的 VLM）独立复核，并用 ROVER 式投票或证据融合。`confirmed` 拆成 `confirmed_same_engine` 与 `confirmed_independent`，只有后者可以降低风险等级。

### 34 · VLM 与专用识别的使用约束 `P1`

- **问题**：§11 的 VLM 修复只处理"未确认区域"，思路好。但 VLM 会对看不清的数字"合理猜测"，且图像里的文字可能含提示注入（如"忽略以上指令……"）。
- **建议**：
  - 把 VLM 限制为闭集任务（只读数字或日期、限定输出格式、temperature=0），输入仅为裁剪图，不带全文上下文。
  - 输出视为不可信数据，必须与至少一个 OCR 候选一致，或通过校验位/算术校验，才能升级状态。
  - 记录模型版本与请求哈希；外发前做 PII 评估与脱敏（见 #49）。

### 35 · 恢复收益以启发式分数变化为目标，且缺少探索 `P1`

- **问题**：§11.2 用"质量分提升 > 0.005"统计恢复成功率，先验强度 4，最少 5 个样本。一是衡量的是启发式分数而不是真实准确率；二是"净值为正才执行"，早期偶然低收益的动作会被永久跳过，再也积累不到样本（选择偏差）。
- **建议**：以人工修订与标注结果为锚，定期校验"分数提升—真实 CER 下降"的相关性。按（问题类型 × 文档类型）分层统计；加入少量强制探索（ε-greedy 或 Thompson 采样）；提高样本阈值，并给出置信区间。

### 36 · 验证"结果选择"本身的准确性 `P1`

- **问题**：§11.5 的分层选择（硬性风险 → 关键字段覆盖 → …… → 融合分）设计合理，但没有数据证明它选到了真实更好的结果，触发与选择用的又是同一套启发式信号。
- **建议**：在标注集上计算"选择准确率"和"与最优候选的差距（oracle gap）"，并报告每个恢复阶段对真实 CER 和字段准确率的边际提升及成本。提升不显著的阶段降级或移除。

### 37 · 以风险—覆盖与不对称成本确定阈值 `P1`

- **问题**：§14.7 以 Youden J 为主确定复核阈值，等价于漏检与误报同权重，而金额错误的代价远大于多一次复核。
- **建议**：按字段类别设定目标，例如"自动通过的金额字段错误率 ≤ ε"，用保形风险控制（conformal risk control）或 Learn-then-Test 在标注集上取得有统计保证的阈值。同时展示"该风险下可自动通过的覆盖率"，让业务按成本取舍。

### 38 · 对 `pass` 文档做随机审计，估计"静默错误率" `P0`

- **问题**：§15、§14.1 的人工复核与样本池主要来自 `review/fail`、低置信、投诉和修订，被判 `pass` 的文档几乎无人复核。后果：(1) 无法估计漏检率；(2) 阈值与校准只用被标记的样本拟合，存在选择偏差，会系统性高估可靠性。
- **建议**：每个文档类型、每个组织每周随机抽 1–5% 的 `pass` 文档做双人标注，输出"静默错误率"及 Wilson 区间。这批样本同时作为无偏校准集，并纳入门禁。

### 39 · 截断与超时：页级分片、可续跑、分优先级队列 `P1`

- **问题**：§17.1 对单份 PDF 最多 OCR 100 个扫描页，时间预算 240 秒（约 2.4 秒/页）。CPU 上 100 页扫描件大概率完不成（需实测），结果只能 `truncated`，后面的页面无人处理。§2 的队列以附件为单位，Worker 是单进程。
- **建议**：把大文档拆成页级任务，并行且可续跑；截断改为"部分完成 + 自动续排"。队列按交互/批量分优先级，按租户限流。截断文档在业务侧强制标注"不完整"，禁止下游当作完整结果消费。

### 40 · 人工复核流程：高价值强制复核、双录与效率指标 `P1`

- **问题**：§15 的复核入口提供原文、候选和诊断，但没有说明：高金额字段是否即使 `pass` 也强制复核；是否有制单—复核（maker-checker）；复核人一致性与效率怎么度量。
- **建议**：按业务金额与风险等级设置"必须人工确认"的规则；关键字段双录或抽检；记录每字段复核耗时、复核人间一致率、修订率。待办按风险排序，支持键盘快捷与批量确认，指标回流到优化台账。

### E. 评测与发布（41–45）

### 41 · 字段准确率的"出现在全文"口径易产生假阳性 `P0`

- **问题**：§13.2 的字段准确率是"归一化后逐字段判断是否出现在全文"。真值 `12,800.00` 只要在全文任何位置出现（比如另一处小计）就判命中，即使字段抽错了位置或角色。字段数量少时尤其乐观。
- **建议**：真值中加入字段所在页、区域和键名，命中判定要求"在对应区域，或与对应标签关联"。保留现口径作为"弱命中"，另报"强命中"，门禁用强命中。

### 42 · CER 归一化会掩盖符号与标点错误 `P0`

- **问题**：§13.2 的 CER 是"小写并只保留字母、数字与 `%`"，数值 CER 还去除千分位。小数点或逗号错位、负号丢失、括号负数、币种符号、全半角差异都可能在这两个指标里"消失"，而这恰恰是金额类业务损失最大的错误。
- **建议**：新增"关键符号错误率"（小数点、千分位、负号、括号、币种符号、百分号），纳入门禁与业务损失。保留标点的原始 CER，至少在金额与表格类文档上作为门禁指标之一。

### 43 · 门禁用点估计，且对金额偏松 `P0`

- **问题**：§13.3 默认字段准确率 ≥ 0.95、全对率 ≥ 0.8，按点估计判断，Wilson 区间只展示。语料较小（§13.1 自述）时点估计很容易"碰巧通过"，而金额字段 5% 的错误率在多数业务里不可接受。
- **建议**：门禁判据改用 Wilson 或 Clopper-Pearson **下界**。按字段类别分设门禁（金额/账号 ≥ 99%，日期、编号次之）。设最小样本量，样本不足时输出"证据不足"，而不是通过。

### 44 · 显著性检验：方法选择、多重比较与文档聚类 `P1`

- **问题**：§14.5 对"按文件配对的 CER 胜/负/平"做精确 McNemar，实质上是符号检验，忽略差异幅度。实验最多 12 个变体，存在多重比较。同一模板、同一客户的文件彼此相关，独立性假设不成立。
- **建议**：用配对 bootstrap 或 Wilcoxon 符号秩检验评估 CER 差；多变体用 Holm/BH 校正；按模板或客户做聚类（block）bootstrap。同时要求"非劣效"：任一关键分组（文档类型、语言、难度）不得显著变差。

### 45 · 数据集隔离、防过拟合与合成数据扩充 `P0`

- **问题**：§13、§14.7、§16.2 中，基准语料既用于调参、对照实验和发布门禁，又"可用最近基准样本重新拟合"阈值——开发集与门禁集重叠，会逐步过拟合。真实语料规模小，train/val/test 隔离要到 §20.3 Phase 2 才规划。
- **建议**：现在就把语料切成 dev / calibration / 盲测集，同模板整体划入同一集合。盲测集只用于门禁并定期更新。用"渲染文本 + 受控退化（模糊、JPEG、噪声、倾斜、阴影、印章叠加）"生成带精确真值的合成数据，扩充回归集（单独成层，不进入门禁）。

### F. 生产治理与工程（46–50）

### 46 · 主动学习：去重、多样性与权重调参 `P1`

- **问题**：§14.1 的优先级权重（0.3/0.3/0.25/0.1/0.05）是固定值。去重键是 `sha256 + 错误类型`，同一模板的不同文件不会被合并，高不确定样本会被同模板大量占满名额。缺少随机对照来验证"主动采样比随机更省标注"。
- **建议**：加入模板或版式聚类与近重复检测，按簇限额；采样时混入一部分随机样本；用"每标注 100 条发现的真实错误数"评估策略，并据此调权重。

### 47 · 漂移检测增加输出侧与内容侧信号 `P1`

- **问题**：§14.3 只比较六类元数据分布，文档自己也说"分布稳定不代表内容质量稳定"。新模板、新字体、新语言混合而元数据不变时无法发现。
- **建议**：增加输出侧指标（置信度直方图、复核/失败/截断率、文字高度、字符集与数字占比、表格占比）和版面特征漂移。用 PSI 或 JS 散度，按文档类型、租户分别建基线。告警联动补标注与门禁复评。

### 48 · 灰度晋级：按分组做非劣效，生产指标不能只靠启发式分 `P1`

- **问题**：§14.5 自动晋级条件是基准样本 ≥ 20、领先边际 ≥ 0.01、生产分不明显偏低。生产分仍是启发式质量分，样本量也偏小。整体更优的模型可能在发票金额这类关键分组上变差（§20.2 也把分流列为后续项）。
- **建议**：晋级要求关键分组非劣效；生产侧用"人工修订率 + 随机审计（#38）"校验；高风险业务保留人工审批；采用序贯检验，或让最小样本量随边际大小动态调整，而不是固定 20。

### 49 · 隐私、合规与数据生命周期 `P0`

- **问题**：文档强调默认本地处理、外部 VLM 需合规确认（§20.1），但没有覆盖：
  - OCR 文本与字段（账号、证件号、金额）在 SQLite 中的静态加密与访问审计；
  - 反馈池、裁剪图、版本链、知识图谱里的 PII 扩散；
  - 内容哈希缓存跨工作区复用带来的"他人文档是否存在"侧信道；
  - 删除请求如何级联到缓存、样本池、版本链、基准语料；
  - 日志里是否含文本片段。
- **建议**：缓存默认按租户隔离；敏感字段脱敏存储与展示；统一保留期和删除级联（含样本池与基准库）；外发 VLM 前做 PII 检测与脱敏或白名单；日志只记元数据；知识图谱与看板加细粒度权限与审计。

### 50 · 工程：可扩展性、可观测性与 sidecar 安全默认值 `P1`

- **问题**：§4.1 单进程锁串行执行；队列是 SQLite，Worker 在 Node 进程内每 5 秒轮询；§4.4 "未配置 token 时不做鉴权"，且 sidecar 通过共享路径读文件。单机小规模足够，但吞吐、故障隔离和默认安全偏弱。
- **建议**：
  - sidecar 多副本 + 客户端负载均衡，必要时用 GPU 或高性能推理后端并做批处理。
  - 队列迁移到支持并发与可见性超时的存储，或至少压测 SQLite 写入。
  - 生产环境强制配置 token、仅监听内网或本地，启用 mTLS 或服务网格。
  - 补齐指标（队列深度与年龄、各阶段耗时与成功率、复核率、成本/文档）、分布式追踪与 SLO 告警。
  - 锁定依赖版本与容器镜像摘要，并写入运行时指纹，保证可复现。

## 五、补充：第二轮复查（新增 23 条，编号 51–73）

> 第二轮重点复查了状态机、限额配置、质量评分细节、评测口径和治理公式，以下均与前 50 条不重复。

### G. 稳定性与工程细节（51–57）

### 51 · 用租约心跳替代固定超时判定"中断" `P0`

- **问题**：§3 规定任务 `processing` 超过 `OCR_TIMEOUT_SECONDS + 60s`（默认 360 秒）就重新排队。而首次抽取（PDF 时间预算 240 秒）加上级联（预算 180 秒，每步请求超时 300 秒）的总时长可能超过 360 秒（需确认总时限是否有统一上界）。任务仍在运行就被另一个 worker 领走，会造成重复处理、结果互相覆盖。
- **建议**：worker 定期续租（heartbeat），只有心跳超时才视为中断；写回结果时带版本号或领取令牌，过期租约的写入直接拒绝。

### 52 · 区分"文档有问题"与"服务不可用"，加熔断 `P1`

- **问题**：§3 对失败有 3 次尝试、退避 60 秒 × 次数。若 sidecar 重启或模型加载期间（`ready=false`）一批任务连续失败，可能把大量正常文档耗尽尝试次数后标为 `failed`（日志里有 `ocr.deferred`，可能已部分处理，需确认）。
- **建议**：连接失败、5xx、`ready=false` 不计入尝试次数，而是整体暂停领取（熔断）并指数退避探活；只有"同一文档在健康服务上反复失败"才计数，并进入死信队列供人工查看。

### 53 · 截断说明写进了 `ocr_text`，污染正文 `P0`

- **问题**：§5.2-8、§3 规定截断时"在文本尾部说明已识别页数"。这属于带内标记，下游检索、字段匹配、基准比对、知识图谱都会把这句话当正文；基准里还会拉高 CER。
- **建议**：截断信息只放元数据（`truncated`、`processedPages`、`totalPages`），不写进正文。UI 与 API 单独展示；如需在文本里提示，使用独立的、可被过滤的字段。

### 54 · 限额配置自洽性校验 `P1`

- **问题**：多处上限互相矛盾：§8.1 的 DIR 上限是 200 页、100k 字符；§17.1 的 `OCR_MAX_PDF_TOTAL_PAGES=1000`、`OCR_MAX_CHARACTERS=500000`、Docling 500 页（§17.5）。数字 PDF 的原生页不计入 OCR 页数上限（§5.2-4），所以一份 1000 页的数字 PDF 会在 DIR 层被截断，而前面的限额都不会提示。
- **建议**：启动时做配置交叉校验（各层上限必须单调一致），冲突就报错或告警；各层触发截断时统一写入 `truncated.reason` 与触发层级；基准和看板按截断原因分类统计。

### 55 · 静默降级必须可见 `P1`

- **问题**：§4.1 模型回退链（v6 → v5 server → Paddle 默认 → 不带方向分类）和 §4.2 的 Docling 回退，都会在失败时自动换成更弱或语义不同的路径。缓存键里有模型标签，但生产或基准可能在不知情的情况下跑在降级模型上，准确率与门禁结论随之失真。
- **建议**：回退发生时在 `/health`、结果元数据、告警中显式标记 `degraded` 与原因（`fallbackReason`）。基准与发布门禁在降级状态下拒绝产出"通过"；生产允许按文档类型配置"宁可延迟或失败，也不降级"。

### 56 · 区域复认批量化，并缓存渲染结果 `P1`

- **问题**：§4.4 的 `/extract-region` 一次只识别一个区域，§11.3 每个关键字段最多复认 4 个区域 × 2–3 遍。若每次调用都重新打开 PDF 并渲染整页，大页高 DPI 下耗时主要花在重复渲染上。
- **建议**：提供批量区域接口（同一页多个 bbox 一次渲染、一次传输、批量推理）；在 sidecar 内缓存近期渲染页（按文件哈希 + 页码 + DPI）。复认名额按字段风险权重（如 §13.2 的金额/账号 8）排序，并随剩余时间预算动态调整，而不是固定 4 个。

### 57 · 重跑与基准任务的配额与资源隔离，失败结果做负缓存 `P1`

- **问题**：§16.1 项目可写用户即可重跑并指定 `mode`/`dpi`（最高 400 DPI），没有提到频率配额，会放大成本；`POST /api/ocr/lab/run`、对照实验是重负载，可能与生产队列争抢同一 sidecar。另外质量 `fail` 的结果不参与缓存复用（§12），同一份坏文件被反复上传，每次都会完整跑一遍级联。
- **建议**：重跑按用户、租户设配额与冷却；基准、实验使用独立队列或独立 sidecar 实例，生产队列优先。对 `fail` 结果保存短 TTL 的"失败指纹"：相同输入与配置下直接返回"已知低质量"，只在配置变化或人工强制时重跑。

### H. 识别与版面（58–63）

### 58 · `auto` 路径下局部旋转文字的低成本探测 `P1`

- **问题**：§4.1 为速度关闭了文本行方向分类，只保留页面级方向。页面内局部旋转的文字（竖向表头、倒置的单据联、旋转印章文字）要等整体质量下降后才进入 `enhanced`，而它们的低置信可能被页面平均值稀释。
- **建议**：在预检或检测阶段统计"高宽比异常的竖长框"与低置信行占比，超过阈值就仅对这些区域启用文本行方向分类，而不是整页切到 `enhanced`。

### 59 · 透视/去倾斜默认关闭，改为按预检自适应启用 `P1`

- **问题**：§7.2 中 `OCR_PREPROCESS_GEOMETRY` 默认为 0，而预检已经测出 `skew`、方向与文档轮廓。倾斜超过阈值（默认 3°）或检测到四边形文档轮廓的手机照片，仍然默认不矫正。
- **建议**：按预检结果自适应启用（倾斜 > 阈值，或检测到透视四边形），并用基准里的"照片/倾斜"分层验证收益；默认关闭可保留给扫描件。每次矫正保留变换矩阵，坐标反算已有设计，直接复用。

### 60 · 基于墨迹的漏识别检测 `P0`

- **问题**：§10 的"文本覆盖率"与 §9.2 的占位值白名单（`-`、`N/A`、`待定`、`无`），都无法发现"该有字却没识别出来"：一个有墨迹的单元格被识别成空或 `-`，既不低置信，也不算异常。
- **建议**：对二值化后的页面做连通域/墨迹密度分析，找出"有墨迹但没有任何识别框覆盖"的区域，以及"单元格墨迹很重但文本为空或为占位值"的情况，生成 `ink_without_text` 问题并触发区域复认。这是目前少有的、与识别置信度无关的漏检信号。

### 61 · 复认裁剪应受单元格/行边界约束 `P1`

- **问题**：§11.3 复认用 35%、60%、100% 的外扩边距。表格里相邻单元格距离很近，外扩后会把邻格内容带入裁剪，复认结果读成"自己 + 邻格"，反而与原值不一致，产生假的 `conflict`。
- **建议**：外扩边距在单元格或文本行边界处截断；若裁剪内含多个检测框，只取与目标框重叠最大的那一个；复认结果与原值比较时，先校验"裁剪里是否只含一个目标文本"。

### 62 · 文本层交叉验证不一致时，改为"双轨呈现"而非只打标 `P1`

- **问题**：§5.2-3、§11.1 规定原生文本不改写，不一致只生成 `text_layer_mismatch` 并触发复核；§11.1 又规定 native 路径不恢复。结果是复核人只看到"有差异"，却没有 OCR 那一侧的完整文本可对照。
- **建议**：对不一致页保存视觉 OCR 的完整结果作为并行候选（不替换原生文本），复核界面并排展示差异位置，并把差异按"数字/非数字"分类。这与"不自动改写"原则并不冲突。

### 63 · 日期歧义与纪年 `P1`

- **问题**：§9.2–9.3 只提到日期解析与范围检查，没有提到：`01/02/2024` 的日月顺序歧义；台湾"民国 113 年"、日本"令和 6 年"等纪年；`2024.1.2`、`二〇二四年` 等写法。解析错了不会报错，只会得到一个"合法但错误"的日期。
- **建议**：用文档语言、地区、同列其他日期（出现 `13/02` 即可锁定顺序）推断日月顺序；增加纪年与中文数字日期解析；歧义时保留多个候选并降低字段置信等级，而不是默默选一个。

### I. 质量评分与评测（64–70）

### 64 · 旧引擎的宽松路径给了 0.75 的默认置信度 `P0`

- **问题**：§10.1 规定没有 DIR 的旧引擎，缺失置信度但有文本时记 0.75。而默认复核阈值是 0.7，0.75 本身就在 `pass` 一侧；若其他信号都不适用或为中性，文档可能被直接判 `pass`，等于对"没有任何质量证据"的结果放行。
- **建议**：没有置信度时按"未知"处理：默认 `review`，或赋予低于复核阈值的保守值；同时把这类结果的占比放进看板，推动旧引擎迁移到 DIR。

### 65 · 质量按页、按来源分层计分，文档取最差页 `P1`

- **问题**：§10 的信号看起来以文档为单位聚合。混合 PDF 里原生页本身没有 OCR 置信度（若记为 1.0 会抬高平均分，也稀释低置信占比的分母），少数扫描页的问题会被大量原生页平均掉；长文档里一页严重错误也容易被均值淹没。
- **建议**：先按页、按来源（native / OCR / embedded_image）分别评分，再用"最差页 + 加权平均"的方式汇总；人工复核也按页或区域派单，而不是让复核人在整份文档里找问题页。

### 66 · 发布门禁默认不含 PDF，原生与混合路径没被覆盖 `P0`

- **问题**：§13.1 写明基准"默认跳过 PDF；Ops 页面可选择包含 PDF"。而方案的核心卖点恰恰是 PDF 原生抽取、逐页路由、文本层可信度与混合处理，这些路径在默认的门禁里没有被测到。
- **建议**：门禁必须包含 PDF（原生、扫描、混合三类各自成层）。耗时问题用"缓存已跑结果 + 增量运行 + 抽样分层"解决，而不是默认跳过；Ops 页面把"本次是否含 PDF"作为门禁结论的显式前置条件。

### 67 · 门禁与验收的样本量规划 `P1`

- **问题**：§20.3 的验收写"每类 ≥ 200 份审核样本"，但没有说明这个数量能证明什么。例如要以 95% 置信度证明某字段类别错误率 ≤ 1%，在零错误的理想情况下大约需要 300 个独立样本（"三之法则" 3/n）；同一模板内字段相互相关，有效样本更少。
- **建议**：按每个门禁指标（金额准确率、全对率、TEDS……）做样本量/功效计算，并把"所需样本量"随结果一起展示；样本不足就标"证据不足"，不要用小样本的好看数字放行。

### 68 · 优化台账的排序公式与"成本—准确率前沿" `P1`

- **问题**：§14.4 的排序分是 `expectedGain / max(0.1, 实现成本 + 推理成本)`，没有使用已记录的"风险"字段，也没有把"该错误类型在生产中的占比与业务损失"作为输入；`expectedGain` 由人估计，难以校验。§13 的基准虽然记录了耗时，但没有"每个正确字段的成本"这类统一目标。
- **建议**：预期收益 = 该错误类型的生产占比 × 业务损失权重 × 预计可解决比例，数据取自错误分类与看板；排序加入风险与不确定性折扣。基准同时输出"准确率—耗时/成本"的帕累托前沿，用"每个正确字段的成本"选择级联与模型配置。

### 69 · 把人工修订当作标注前，先做质检 `P1`

- **问题**：§15、§14.1 把字段修订直接回流为标注与校准输入。复核人也会出错或理解不同，修订本身没有二次确认，标签噪声会直接污染阈值拟合与主动学习。
- **建议**：对修订样本做双人确认或按比例抽检，记录复核人一致率；高分歧样本进入仲裁；拟合与评测时带上标注可信度（如已双确认 / 单人）。对只有单人修订的样本降权或不进入盲测集。

### 70 · 阈值 profile 用分层收缩，而不是"逐级回退" `P2`

- **问题**：§14.7 在 profile 不可用时按"最具体且已校准的维度回退到整体"。多个维度同时命中（如 `kind=发票` 与 `workspace=A`）时优先级不明；小样本 profile 的阈值噪声大，要么用得不稳，要么完全不用。
- **建议**：用分层贝叶斯或经验贝叶斯式的收缩：小样本维度向整体阈值收缩，样本越多越接近自身估计；并明确多维度冲突时的合成规则与可解释输出。

### J. 治理与数据（71–73）

### 71 · 知识图谱的假关联风险 `P1`

- **问题**：§14.6 把金额作为实体，同一金额出现在多个附件就建立 `shared` 关系；`mentions` 靠字符串包含。常见金额（如 `100.00`）与短编号会产生大量无关联系，使"跨文档关联"的精度很差，对账结论可能被误导。
- **建议**：金额类关联要求联合键（金额 + 日期 + 对手方或编号）；编号设最小长度和类型约束；按实体出现频率做 IDF 降权，高频实体不建边；每条关系附带"依据与置信度"，并在 UI 区分"强关联 / 弱关联"。

### 72 · 漂移基线的季节性与告警去噪 `P2`

- **问题**：§14.3 的基线是人工保存的静态快照，阈值固定 0.2。月末、季末、年度结算期，发票与对账单占比会周期性变化，会产生规律性的误报，久了运维会忽略告警。
- **建议**：基线采用滚动窗口，并按周/月/季做同期对比；告警加冷却与合并；严重告警才联动补标注，轻度告警只进周报。

### 73 · 利用 PDF 元数据与生成来源作为路由先验 `P2`

- **问题**：§5.2 对每页都是"先算文本层可信度，再决定"。PDF 的 Producer/Creator、是否整页单图、字体嵌入情况，其实能廉价地判断它来自 Word 导出、系统生成，还是扫描仪、手机扫描 App。
- **建议**：把这些元数据作为先验写入路由原因：系统生成的 PDF 降低交叉验证抽样率，疑似"扫描 + 第三方 OCR 层"的 PDF 提高抽样率并进入 #02 的加强检查。
